# 生产级/竞赛级改进建议

## 概述

基于当前平台工程设计方案的审查，虽然整体闭环架构设计清晰，但要达到生产级/竞赛级（高质量）交付标准，需要在以下几个关键维度进行改进和补强。

---

## 一、架构与数据链路改进

### 1.1 防抖去重机制

#### 现状问题
方案提出了"重复事件去重"，但未明确具体算法。如果AI算法以30 FPS的帧率持续上报HIGH风险，数据库可能会瞬间被写入挤爆。

#### 改进方案
**增加事件防抖阈值（Cooldown/Debounce）**

规定同一设备、同一风险类型在 N 秒内（如10秒）只生成一次新告警或写入记录，后续重复事件仅更新最后活跃时间或计数器。

**实现方案：**
- 采用滑动窗口算法（Sliding Window）
- 使用Redis存储最近N秒的事件指纹（device_id + risk_type + risk_level）
- 后端增加`event_deduplicator.py`服务

**代码位置：**
```
backend/app/services/event_deduplicator.py
backend/app/services/alert_service.py (增强去重逻辑)
```

**优先级：** ⭐⭐⭐⭐⭐ 高

---

### 1.2 视频流延迟与传输协议优化

#### 现状问题
萤石平台默认的HLS/EZOPEN协议通常有3~8秒的延迟，对于"跌倒风险/实时告警"等强时效场景延迟过高。

#### 改进方案
**采用低延迟传输协议**

前端监控和AI推理取流推荐优先采用 **WebRTC** 或 **HTTP-FLV / WebSocket-FLV** 低延迟传输协议，将画面延迟控制在1秒以内。

**实现方案：**
1. 查询萤石平台是否支持WebRTC/FLV流
2. 如果支持，在`ezviz_service.py`中增加获取FLV流地址的方法
3. 前端使用`flv.js`或`WebRTC`库替代HLS播放器
4. AI推理侧直接拉取FLV流进行分析

**技术选型：**
- WebRTC（延迟<500ms，首选）
- HTTP-FLV + flv.js（延迟1~2s，备选）
- RTMP推流 + FFmpeg转码（最后方案）

**优先级：** ⭐⭐⭐⭐ 高

---

### 1.3 告警状态机缺少"超时自动升级/处理"

#### 现状问题
当前状态机仅支持 NEW → NOTIFIED → CONFIRMED → RESOLVED。如果发生HIGH/CRITICAL高危告警后，工作人员长时间未点击确认，系统缺乏应对措施。

#### 改进方案
**增加超时升级机制（Escalation）**

若高危告警在M分钟内（如5分钟）处于NEW或NOTIFIED状态未被处理，状态自动转为`UNHANDLED_ESCALATED`，并通过WebSocket全屏闪烁强提醒或触发二次推送。

**实现方案：**
1. 增加后台定时任务（APScheduler或Celery Beat）
2. 每分钟扫描未处理的高危告警
3. 超时后自动升级状态并推送紧急通知
4. 前端监听`ESCALATED`类型消息，触发全屏红色闪烁

**数据库字段补充：**
```python
# alerts表增加
escalation_level = Column(Integer, default=0)  # 0-正常, 1-首次升级, 2-二次升级
escalated_at = Column(DateTime(timezone=True))
```

**优先级：** ⭐⭐⭐⭐⭐ 高

## 二、接口与数据模型改进

### 2.1 缺少"抓拍图/证据链"生成逻辑

#### 现状问题
告警表`alerts`包含`snapshot_url`，但未说明图片从何而来（是AI上传、后端调用萤石API抓拍，还是前端截图）。

#### 改进方案
**明确抓拍图链路**

当接收到AI的`POST /api/v1/ai/events`且风险等级为高时，后端同步或异步调用萤石抓拍接口，并将返回的图片存储到本地静态目录或云存储。

**实现流程：**
1. AI上报HIGH风险事件 → 后端接收
2. 后端立即调用萤石抓拍接口`/streams/{id}/snapshot`
3. 获取图片URL或Base64数据
4. 将图片保存到`/static/snapshots/{device_id}/{timestamp}.jpg`
5. 将相对路径写入`alerts.snapshot_url`

**代码增强：**
```python
# backend/app/services/alert_service.py
async def create_alert_with_snapshot(self, risk: RiskRecord, db: Session):
    # 高风险才抓拍
    if risk.risk_level == "HIGH":
        snapshot_url = await ezviz_service.capture_and_save(risk.device_id)
    else:
        snapshot_url = None
    
    alert = Alert(
        device_id=risk.device_id,
        snapshot_url=snapshot_url,
        ...
    )
```

**优先级：** ⭐⭐⭐⭐ 高

### 2.2 SDNL1雷达接口时序与数据清洗处理

#### 现状问题
毫米波雷达容易受到环境干扰（如窗帘摆动、宠物移动）产生噪点数据（如心率瞬间变为0或200）。

#### 改进方案
**后端数据清洗与异常值过滤**

后端接入雷达数据时，不能直接盲目入库，需加入移动平均滤波/异常值剔除。

**实现方案：**
```python
# backend/app/services/health_validator.py
class HealthDataValidator:
    HEART_RATE_RANGE = (30, 180)      # 正常心率范围
    RESPIRATORY_RATE_RANGE = (8, 30)  # 正常呼吸范围
    
    def validate(self, data: HealthCreate) -> HealthCreate:
        # 心率异常检测
        if data.heart_rate:
            if not (self.HEART_RATE_RANGE[0] <= data.heart_rate <= self.HEART_RATE_RANGE[1]):
                data.heart_rate = None  # 标记为无效
        
        # 呼吸率异常检测
        if data.respiratory_rate:
            if not (self.RESPIRATORY_RATE_RANGE[0] <= data.respiratory_rate <= self.RESPIRATORY_RATE_RANGE[1]):
                data.respiratory_rate = None
        
        return data
```

**增加移动平均滤波：**
- 保留最近10个有效数据点
- 计算滑动平均值，剔除突变点
- 数据库增加`raw_value`和`filtered_value`字段

**优先级：** ⭐⭐⭐⭐ 高

### 2.3 前端WebSocket断线心跳与重连机制缺失

#### 现状问题
仅提到"断线重连"，未提及心跳包（Ping/Pong）。若长时间无事件推送，TCP连接可能被Nginx或防火墙暗中切断，导致前端"假在线"。

#### 改进方案
**增加客户端-服务端双向Ping/Pong心跳包**

**实现方案：**
```typescript
// frontend/src/hooks/useWebSocket.ts
useEffect(() => {
  let pingInterval: NodeJS.Timeout
  
  const connect = () => {
    const ws = new WebSocket(wsUrl)
    
    ws.onopen = () => {
      // 启动心跳
      pingInterval = setInterval(() => {
        if (ws.readyState === WebSocket.OPEN) {
          ws.send('ping')
        }
      }, 30000)  // 每30秒ping一次
    }
    
    ws.onmessage = (event) => {
      if (event.data === 'pong') {
        lastPongTime = Date.now()
        return
      }
      // 处理业务消息...
    }
    
    // 检测超时
    const timeoutCheck = setInterval(() => {
      if (Date.now() - lastPongTime > 60000) {
        ws.close()  // 超时强制断开重连
      }
    }, 10000)
  }
}, [])
```

**后端增强：**
```python
# backend/app/main.py
@app.websocket("/ws/{client_id}")
async def websocket_endpoint(websocket, client_id: str):
    await websocket_manager.connect(websocket, client_id)
    try:
        while True:
            data = await websocket.receive_text()
            if data == "ping":
                await websocket.send_text("pong")  # 立即回应
    except Exception as e:
        websocket_manager.disconnect(client_id)
```

**优先级：** ⭐⭐⭐⭐⭐ 高

## 三、工程化与部署改进

### 3.1 缓存层与队列保障（提升高并发/稳定性）

#### 现状问题
MVP阶段未引入Redis，所有设备状态、最新Token、WebSocket连接信息均保存在内存或直接查PostgreSQL，容易引发数据库IO瓶颈。

#### 改进方案
**抽离Cache Service抽象层**

虽然MVP阶段可不强制安装Redis，但后端代码层必须抽离出`Cache Service`抽象层。

**实现架构：**
```python
# backend/app/services/cache_service.py
from abc import ABC, abstractmethod

class CacheService(ABC):
    @abstractmethod
    async def get(self, key: str): pass
    
    @abstractmethod
    async def set(self, key: str, value: any, ttl: int = 300): pass

class MemoryCache(CacheService):
    """内存缓存实现（MVP阶段）"""
    def __init__(self):
        self._cache = {}
    
    async def get(self, key: str):
        return self._cache.get(key)
    
    async def set(self, key: str, value: any, ttl: int = 300):
        self._cache[key] = value

class RedisCache(CacheService):
    """Redis缓存实现（生产环境）"""
    async def get(self, key: str):
        return await redis_client.get(key)
```

**使用场景：**
- 缓存萤石AccessToken（避免频繁申请）
- 缓存设备在线状态（避免频繁查库）
- 缓存最新风险分数（Dashboard快速展示）

**优先级：** ⭐⭐⭐⭐ 高

---

### 3.2 缺少模拟数据生成器（Mock Engine）的自动化脚本

#### 现状问题
当前的Mock只是静态的`.json`配置文件，缺乏动态变化。

#### 改进方案
**编写动态模拟数据生成脚本**

按时间正弦曲线/随机游走生成数据，动态模拟心率（60~90）、呼吸（12~20）以及偶发跌倒事件。

**实现方案：**
```python
# mock/dynamic_mock_generator.py
import math
import time
import random

class DynamicMockGenerator:
    def generate_realistic_heart_rate(self, base=72):
        """基于正弦波 + 随机噪声生成心率"""
        t = time.time()
        # 正弦波模拟昼夜节律
        sine_wave = 10 * math.sin(t / 3600)  # 1小时周期
        # 随机噪声
        noise = random.uniform(-5, 5)
        return int(base + sine_wave + noise)
    
    def generate_fall_event(self, probability=0.02):
        """以2%概率生成跌倒事件"""
        if random.random() < probability:
            return {
                "risk_score": random.uniform(0.85, 0.95),
                "risk_level": "HIGH",
                "status": "falling",
                "reasons": ["检测到快速下坠", "身体姿态异常"]
            }
        return None
```

**优先级：** ⭐⭐⭐ 中

### 3.3 数据库日志与审计记录（系统日志表补全）

#### 现状问题
包含`system_logs`表，但未定义分类。

#### 改进方案
**明确日志级别与日志来源**

**数据库表增强：**
```python
# backend/app/models/system_log.py
class SystemLog(Base):
    __tablename__ = "system_logs"
    
    id = Column(Integer, primary_key=True)
    source = Column(String(50), nullable=False)  # EZVIZ_SDK, AI_ENGINE, WEBSOCKET, USER_ACTION
    level = Column(String(10), nullable=False)   # INFO, WARN, ERROR, CRITICAL
    message = Column(Text, nullable=False)
    metadata_ = Column("metadata", JSON, default={})
    created_at = Column(DateTime(timezone=True), server_default=func.now())
    
    __table_args__ = (
        Index('idx_logs_source_level', 'source', 'level'),
        Index('idx_logs_created_at', 'created_at'),
    )
```

**使用示例：**
```python
# 记录萤石API调用失败
SystemLog.create(
    source="EZVIZ_SDK",
    level="ERROR",
    message="获取设备列表失败",

```

**前端展示：**
增加"系统日志"页面，展示最近500条日志，支持按来源和级别筛选。
